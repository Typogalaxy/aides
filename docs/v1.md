# Aides v1

Aides is a self-hosted personal Agent system. The repository and project directory are named `aides`. Each installation owns its server,
conversations, tasks, files, memory and model accounts. The first release targets
macOS. An iPhone client and QR pairing are backlog items.

## Repository

The root Swift package owns shared dependencies and builds the server, desktop
executable and their libraries. Platform distribution lives in scripts and GitHub
Actions. Application data and signing material live outside the repository.

- AidesCore defines the persistent conversation, project, task and policy model.
- AidesExecution adapts local inference, provider APIs and supported coding tools.
- AidesServer provides persistence, task scheduling, pairing and the client API.
- AidesDesktop provides the native SwiftUI client and the macOS update affordance.

## Implementation and acceptance

1. Establish the root package, domain model and reproducible build.
2. Persist conversations, projects, task progress and run outcomes on the server.
   A restart must restore recorded state, and unknown side effects require
   reconciliation before retry.
3. Pair each Mac independently. The server orders messages and shares progress
   across clients. Bind to loopback by default. Access across machines requires
   a private network and authenticated transport.
4. Run secretary conversations and memory processing locally. Save source-backed
   memories, scoped preferences, source messages and task decisions separately.
   Reload current preferences each turn and compress historical input while
   allowing retrieval of the original evidence.
5. Support secretary, area and project conversations plus bounded Workers.
   An authorized project may reference a working directory. The server owns task
   state. Temporary conversations can be archived with a short report.
6. Persist one-time and recurring schedules. Fire them without leaving the UI
   open, preserve timezone, support cancellations and avoid duplicate dispatch.
7. Configure local model endpoints and supported cloud integrations on the host.
   Pin the model/configuration assigned to each Worker. An unavailable model
   leaves a resumable task and changing defaults applies to later work. Cloud
   access and paid fallback require explicit configuration.
8. Review tool permissions and cloud data boundaries in program logic before
   dispatch. The user sees operations awaiting approval and can stop future work.
   A local model can assist review but does not confer authority. Store external
   credentials on the host and scope any execution to granted resources.
9. Support a structured, by-request review for complex tasks. Independent initial
   interpretations, concrete disagreements, user clarification and bounded
   follow-up should be visible. An individual Worker can use the same or a
   different configured model.
10. Build a desktop experience with conversations, projects, Workers, runtime
    information and settings. The user can inspect a Worker from a conversation.
11. Build/test pull requests on a macOS runner. Stage a tagged DMG release and
    optional signed update feed. Public distribution with Developer ID requires
    developer credentials. Updating the desktop must preserve server state.

## Toolkit

The Toolkit groups actions and resources by purpose. The file catalog is
available at `GET /api/v1/toolkit/catalog`, with `?writes=true` for clients that
support text writes. Paired clients submit actions to
`POST /api/v1/toolkit/invocations` and check the receipt at
`GET /api/v1/toolkit/invocations/{id}`. The server records the requesting device
and routes file work to the target Mac. It retains the 32 most recent terminal
file requests and all active requests. It retains retired invocation IDs to
prevent replay. See the [Toolkit guide](toolkit.md) for permissions, available
service connectors, and setup.
